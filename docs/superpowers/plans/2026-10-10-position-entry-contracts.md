# Position entry contracts for adaptive paper recovery

Goal: preserve each open position's original entry strategy when the supervisor publishes a new version, as required by adaptive-paper-recovery-goal.md criterion4. No model call, deployment, paid service, heavy backtest or real order is part of this change.

Current evidence: Position.strategy_version is persisted, but PositionEngine.process_candle passes the current strategy to evaluate_strategy, trailing-stop logic and partial/full exit handling. Publication archives prior full YAML versions under state/history/vNNNN.yaml. Persisting the version alone does not preserve execution behavior.

Design: inject an optional entry-contract resolver into the paper engine. The configured recovery worker resolves open-position strategy_version against exact archived full strategy bytes, applies the original per-asset override, verifies the declared version, and uses the resolved rules for position management. New entries use the current version. Reuse current resolver rules for asset overrides. Preserve entry-version provenance in decisions and keep archives immutable. Never silently substitute current strategy when a required original contract is missing or conflicting; expose reconciliation status and retain explicit protective handling. Define missing-contract protective behavior before implementation so a metadata failure cannot cause unbounded holding or invent an exit hypothesis.

Verification: enter under version1, publish a changed exit threshold or trailing/partial rule, then verify the open position follows version1 after restart and newly opened positions use version2. Verify retained fee/slippage assumptions and minimums against the distinction between historical experiment rules and externally updated venue constraints. Cover missing, conflicting, malformed and wrong-version archives and partial-close lineage. Use real persistent repository and archived bytes. Run the full test suite and independent review; update graph and evidence. Controlled release still requires market/cost/account-policy validation and prospective adaptive/control setup.

## Implemented design and verification scope

Configured wallets inject EntryContractResolver and preflight all existing positions before processing any symbol. Historical full YAML versions are loaded with Decimal-safe parsing, version and execution-setting checks, then per-asset overrides use the worker merge rules. Existing positions use original exit, trailing, partial and modeled execution-cost rules; new entries use current strategy. Missing/malformed original rules block new entries for the cycle, force an explicitly labeled simulated recovery exit at candle close, retain the original position version and mark heartbeat degraded. This recovery is not an accepted learning hypothesis or proof of profitability.

Nine focused tests cover original take-profit across restart/newentryversion, detached overrides, malformed/wrong-version/path archives, Decimal numeric fees and slippage, old partial fraction and lineage, old trailing multiplier, cross-field exit constraints, and multi-symbol ordering that previously permitted an entry before discovering a broken archive. Independent review found Decimal-merge and incomplete preflight issues; each was reproduced and fixed. Final full verification/re-review remains to record.

Before operational release: wallet liquidation marks must reconcile entry-version cost assumptions with current venue constraints; recovery outcomes must be distinguished from normal adaptive trade evidence, and any historical archive import must use verified original bytes. Current-version lookup binds a detached cycle strategy; it does not certify manually edited same-version configuration. One-writer publication/version checks remain necessary.

Final local verification:725 full-suite tests pass in32.806s; independent read-only follow-up finds no additional important blocker within this stage. Evidence: research/runs/position-entry-contracts-v1/verification.json and full-tests.log. No deployment, model request or real order. Wallet-cost reconciliation and recovery-outcome treatment remain required before activation.
